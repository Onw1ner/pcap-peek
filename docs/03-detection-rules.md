# 检测规则：三条规则各自在判什么

这里的每一条规则都只做一件事：**拿几个数字，判断它们像不像某种行为**。规则不负责抓包，也不负责数数——数数在解析流程里，规则只做判断。

## 三条规则一览

| 规则 | 严重度 | 判断依据 | 阈值 |
|---|---|---|---|
| `syn_scan` | high | 同一源 IP 发起大量 SYN，但完成的极少 | ≥ 20 次 SYN，且完成率 < 30% |
| `dns_tunnel` | medium | 同一基域下出现大量超长随机子域 | ≥ 10 个不同前缀，每个前缀 ≥ 40 字符 |
| `plaintext_credential` | high | 明文协议里出现 Basic 认证头 | 出现即报 |

三条规则的共同点：**只读，不改任何东西**。检测器看到可疑行为只记录，不做阻断——这类工具一旦会动手，就不再是分析工具了。

---

## ① syn_scan：端口扫描

### 在数什么

扫描器的特征不是"SYN 很多"（正常浏览网页也可能一次开几十个连接），而是 **SYN 很多、完成的极少**。

- `syns`：该源 IP 发出的纯 SYN 数量（`flags & 0x02` 且 `!(flags & 0x10)`）
- `completed`：这些目标端口里，后来真的出现了双向数据的目标数量

### 为什么要看完成率而不是只看数量

只看数量会把正常行为全报出来：打开一个网页可能要连 20 多个域名。反过来只看完成率也不行——只连了一次失败也算 0%，但那是打错地址。

两个条件同时成立才报：**规模够大**（≥ 20）+ **成功率够低**（< 30%）。

### 阈值从哪来

- `SYN_SCAN_MIN_SYNS = 20`：一次 `nmap -sS` 扫常见端口就是上百个；20 是"明显不是手动操作"的下限
- `SYN_SCAN_MAX_RATIO = 0.3`：正常业务里失败率很少超过 30%；扫描时通常接近 0%

### 可能误报

- 网管工具批量检查端口存活（批量 ping/telnet）——**行为上真的像扫描**，这类误报只能靠白名单
- 主机重启后批量重连失败的服务

### 怎么调

想更宽松就调大 `min_syns` 或调小 `max_ratio`；想更敏感则相反。两个参数都是函数默认参数，测试里直接传别的值。

## ② dns_tunnel：DNS 隧道

### 在数什么

DNS 隧道把数据编码进**子域名**，所以特征非常具体：同一个基域下，出现大量**很长、互不相同**的前缀。

```
<50 个字符的随机串>.t.evil-dns.com
```

- 拆解域名：`labels = name.rstrip(".").split(".")`
- 少于 4 段直接跳过（`a.b.com` 这种不可能是隧道）
- 基域 = 最后两段（`evil-dns.com`），前缀 = 中间所有段拼接
- 前缀长度 < 40 跳过；同一个基域下**不同前缀的数量** ≥ 10 才报

### 为什么用 set 数"不同的前缀"

隧道每次传的内容都不同，所以前缀几乎不重复。用 `set` 去重能顺带过滤掉"同一域名被查询了很多次"（缓存失效重试）的情况——那种是 1 个前缀、100 次查询，不该报。

### 阈值从哪来

- `DNS_TUNNEL_MIN_LABEL_LEN = 40`：正常子域很少超过 40 字符（CDN、长域名服务商会有，但也少见）
- `DNS_TUNNEL_MIN_SUBDOMAINS = 10`：一次隧道会话不可能只传 10 个包以下

### 为什么严重度只给 medium

**分不清合法和非法**。有些正规服务也会用长随机子域（CDN 分片、某些广告联盟、反欺诈指纹）。这条规则给的是"值得看一眼"，不是"确定是攻击"。

### 可能误报

- CDN / 广告域名的随机子域
- 某些客户端的遥测上报

## ③ plaintext_credential：明文凭据

### 在判什么

HTTP Basic 认证把 `用户名:密码` 做 base64 放在请求头里。base64 **不是加密**，等于明文。

```
Authorization: Basic YWRtaW46c2VjcmV0MTIz
                     └── admin:secret123
```

判断流程：在负载里找 `authorization: basic `（**先 lower() 再找**，因为头名大小写不敏感），取到行尾，`base64.b64decode(..., validate=True)`，提取冒号前的用户名。

### 一条硬规矩：密码不进报告

`detail` 里只放 `user=xxx（密码已隐去）`。测试里那句 `assert "pass" not in finding.detail` 就是在守这条线。

原因不是"怕麻烦"，而是**报告本身会流转**：截图、贴群、写进工单、进日志。一旦密码进了报告，这个工具就从"帮你发现问题"变成"帮你泄露问题"。

### 可能误报

基本没有——出现 Basic 头就是出现 Basic 头，事实陈述。真正的边界在别处：**这条规则只覆盖 HTTP，TLS 里的 Basic 看不到也不该看**。

## 规则与引擎的分界

```
rules.py    纯函数：给定几个数字，返回 Finding 列表。不知道流量的存在。
engine.py   攒证据：边解析边记，最后把数字喂给 rules。
```

这么分的好处是**可以只用三个数字测完一条规则**，不需要造流量：`check_syn_scan("10.0.0.5", syns=30, completed=0)` 就能断言。

如果把"攒证据"和"做判断"写在一起，测试就必须构造完整抓包才能测一条规则——慢、脆、而且测不出边界。

## 复现

```powershell
python demo_suspicious.py
python -m pcappeek stats .\samples\_local\suspicious.pcap
```

样本里有 43 帧：30 个 SYN（零完成）、1 条带 Basic 头的 HTTP 请求、12 条超长子域的 DNS 查询。期望输出：

```
发现: 3 条
  [high] syn_scan 10.0.0.5
      30 次 SYN，仅 0 次完成（0%）
  [medium] dns_tunnel evil-dns.com
      12 个超长子域（长度 >= 40），疑似隧道
  [high] plaintext_credential 10.0.0.6:40001 -> 10.0.0.9:80
      HTTP Basic 凭据：user=admin（密码已隐去）
```

样本写在 `samples/_local/`，已被 `.gitignore` 忽略；**进仓库的是生成脚本本身**，这样别人拿到仓库能自己复现，而仓库体积不会因为抓包文件膨胀。
