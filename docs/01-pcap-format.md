# pcap 文件格式

这篇是本项目唯一的"外部知识依赖"：解析器要处理的每一种字节，都在这里有出处。

> 只讲 **pcap**（libpcap 经典格式）。**pcapng** 是另一套格式（magic `0x0A0D0D0A`），本项目不支持，遇到会明确报错。

## 1. 整体结构

一个 pcap 文件 = **1 个全局头 + N 条记录**，N 可以是 0。

```
┌──────────────┬───────────┬─────────┬───────────┬─────────┐
│ 全局头 24 B  │ 记录头 16B│ 数据 …  │ 记录头 16B │ 数据 …  │
└──────────────┴───────────┴─────────┴───────────┴─────────┘
```

没有文件尾标记，没有记录条数字段。**读到文件末尾（read 返回空）就是结束**。

## 2. 全局头（24 字节）

| 偏移 | 长度 | 字段 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 4 | `magic` | u32 | 标识文件类型 + 字节序 + 时间精度，见下节 |
| 4 | 2 | `version_major` | u16 | 一般为 `2` |
| 6 | 2 | `version_minor` | u16 | 一般为 `4` |
| 8 | 4 | `thiszone` | i32（**有符号**） | 历史字段，通常 `0` |
| 12 | 4 | `sigfigs` | u32 | 历史字段，通常 `0` |
| 16 | 4 | `snaplen` | u32 | 抓包时的截断长度，如 `65535` |
| 20 | 4 | `linktype` | u32 | 链路层类型：`1` = 以太网 |

对应格式串：`<IHHiIII`（小端）。

注意 `thiszone` 是 **`i`（有符号）**，不是 `I`。写错不报错，但值一旦为负就会读成天文数字。

## 3. magic 的四种字节形态

magic 数值固定为 `0xA1B2C3D4`（微秒）或 `0xA1B23C4D`（纳秒）。但**磁盘上的字节顺序取决于导出工具**：

| 磁盘字节 | 字节序 | 时间精度 |
|---|---|---|
| `D4 C3 B2 A1` | 小端 | 微秒 |
| `4D 3C B2 A1` | 小端 | 纳秒 |
| `A1 B2 C3 D4` | 大端 | 微秒 |
| `A1 B2 3C 4D` | 大端 | 纳秒 |

**判断顺序只能是「先取原始 4 字节比较」**——在知道字节序之前，你没法解释这 4 个字节代表什么数。这是一个先有鸡还是先有蛋的问题，必须用字节比。

确定字节序后，整份文件（头 + 所有记录）都按那个字节序解析。

## 4. 记录头（16 字节）

| 偏移 | 长度 | 字段 | 类型 | 说明 |
|---|---|---|---|---|
| 0 | 4 | `ts_sec` | u32 | 时间戳的秒部分 |
| 4 | 4 | `ts_usec` | u32 | 微秒部分（0–999999） |
| 8 | 4 | `incl_len` | u32 | **这条实际存了多少字节** |
| 12 | 4 | `orig_len` | u32 | 原始包长度（可能大于 `incl_len`） |

对应格式串：`IIII`（字节序随全局头）。

记录头之后紧跟 `incl_len` 字节的数据。

### `incl_len` 与 `orig_len` 为什么可能不同

`snaplen` 会限制每条记录最多存多少字节。抓包时设 `snaplen=96`，一个 1500 字节的包会被截断存 96 字节：

```
incl_len = 96      ← 文件里真实的字节数
orig_len = 1500    ← 网线上真实的长度
```

所以读数据永远用 `incl_len`，`orig_len` 只作为信息透传。

## 5. 时间戳

`ts = ts_sec + ts_usec / 1_000_000`，例如 `sec=100, usec=500000` → `100.5`。

**用整数微秒先算再除**，不要先转 float 再算——浮点表示不了所有微秒值，误差会累积。

纳秒精度的文件把后 4 字节解释为纳秒（除以 1_000_000_000），本项目当前按微秒处理，这与上游工具行为一致。

## 6. 畸形输入清单

真实世界里 pcap 文件经常是坏的。以下 8 类都要显式处理，**不允许崩溃，也不允许静默返回错误数据**：

| 症状 | 处理 | 对应用例 |
|---|---|---|
| 文件不存在 / 无权限 / 是目录 | `OSError` → `PcapError` | `test_missing_file_raises_pcap_error` |
| 文件短于 24 字节 | 报"文件太短" | `test_truncated_global_header_raises` |
| magic 不在四种形态内 | 报"不是 pcap 文件" | `test_bad_magic_raises_pcap_error` |
| 只有全局头、无记录 | 正常返回 0 条，**不是错误** | `test_empty_file_has_no_frames` |
| 记录头只剩半个（如 8 字节） | 报"记录头被截断" | `test_truncated_record_header_raises` |
| 数据不足 `incl_len` | 报"数据被截断" | `test_truncated_record_data_raises` |
| `incl_len` 荒谬（如 `0xFFFFFFFF`） | 超上限直接拒，**不先 read** | `test_absurd_incl_len_rejected` |
| 大端文件 | 正常解析 | `test_big_endian_file` |

判断顺序有讲究：

1. 先判空（`read` 返回 `b""`）→ 正常结束
2. 再判长度不足 → 截断错误
3. 最后判 `incl_len` 上限 → **必须在 `read` 之前**，否则内存已经吃掉了

## 7. 实现对应

| 概念 | 代码位置 |
|---|---|
| 格式串与上限 | `pcappeek/pcap.py` 顶部常量 |
| 全局头解析 + 字节序判定 | `PcapReader.__iter__` 开头 |
| 记录循环 | `PcapReader.__iter__` 的 `while True` |
| 一条记录的结构 | `Frame`（`frozen dataclass`） |
| 错误类型 | `PcapError` |

设计约束（详见 README「约定」）：

- 全流式：内存里同时只有一条记录
- `__init__` 不打开文件，只在迭代时打开
- 所有错误消息带 `index`，方便定位是第几条坏的
