# 02 · 抓包时踩到的坑：数字是怎么被污染的

这份笔记记录第一次用真实流量验证时的发现。它比功能本身更值得留档：
**解析器没错，错的是数据源，而我差点把错的数字当成结论。**

## 现象：只有 34% 的帧能被解析

第一次抓包（30 秒浏览网页，`pktmon` 默认参数）：

```
帧总数: 175158
跳过（非 IPv4）: 116502      ← 66%
解析失败: 0
ethertype 分布:
  ~0x7496  59610
  ~0x0800  58656
  ~0x58CB  56856
  0x86DD      30
  0x0806       6
```

`0x7496` 和 `0x58CB` 不是任何已知以太网类型。真实的以太网类型只有
`0x0800`(IPv4) / `0x0806`(ARP) / `0x86DD`(IPv6) 这几个。

## 原因一：Wi-Fi 下同时存在两种链路层封装

把可疑帧的原始字节挖出来看：

```
0x0800 的帧（正常以太网）：
  e0:41:02:d4:89:00 │ 2c:33:58:cb:6c:54 │ 08 00 │ 45 00 ...
  └──── 目的 MAC ───┘ └──── 源 MAC ────┘ └类型┘ └─ IPv4 ─

0x7496 的帧：
  88 02 │ 54 00 │ 2c:33:58:cb:6c:54 │ 98:48:74:96:20:70 │ ... │ 50 1a │ 00 00 │ aa aa 03 00 00 00 08 00
  └FC──┘ └dur──┘ └────── 地址1 ─────┘ └────── 地址2 ────┘       └序号┘ └QoS┘ └───── LLC/SNAP ─────┘
```

`88 02` 是 802.11 的帧控制（Frame Control）：类型=数据、子类型=QoS Data。
后面三个 MAC 地址是 802.11 的标准结构。真正的 IPv4 藏在偏移 26 之后的
LLC/SNAP 头（`aa aa 03` + OUI `00 00 00` + ethertype `08 00`）里。

**结论**：本机走 Wi-Fi 时，`pktmon` 在 NDIS 层同时记录了
「原始 802.11 帧」和「系统转换成以太网的副本」，两种格式混在同一个文件里。

**关键点：pcapng 的 `linktype` 字段仍然写 1（以太网）。**
所以不能靠接口号或 linktype 区分——`pktmon etl2pcap` 把 802.11 帧也标成了以太网。

## 原因二：同一个包在多层被抓了多份

修好封装识别后，解析率到了 99.94%，但 Top 会话的包数比修改前涨了 3 倍：

| 会话 | 修复前 | 修复后 | 倍数 |
|---|---|---|---|
| `10.151.9.139:6210 <-> 64.233.188.207:443` | 38908 包 | 116374 包 | 2.99× |

会话数（五元组）没变，包数涨 3 倍 = 同一个包被记了多份。

按 `(时间戳, 五元组, 完整负载)` 精确去重：

```
IPv4 帧总数:              175056
按微秒时间戳去重后:       132365
每个重复组里的份数:        {1: 106320, 2: 17236, 3: 3647, 4: 2993, 5: 1663, 6: 506}
```

**24% 的帧是重复捕获。**

原因：`pktmon start` 默认 `--comp all`，会在协议栈多个组件上各捕获一次。

## 解决方法：从源头抓干净，而不是在代码里补救

```powershell
pktmon start --capture --pkt-size 128 --comp nics -f C:\Users\Dan\pktmon2.etl
REM 使用 30 秒
pktmon stop
pktmon etl2pcap C:\Users\Dan\pktmon2.etl -o samples\_local\real-nics.pcapng
```

`--comp` 的三档取值：

| 值 | 含义 |
|---|---|
| `all`（默认） | 所有 NDIS 组件 → 同一个包在每层各留一条 |
| `nics` | 只抓网卡这一层 → 每个包只出现一次 |
| `<id> <id> ...` | 精确指定（`pktmon comp list` 查看） |

结果：

```
帧总数: 3494
跳过（非 IPv4）: 11
解析失败: 0
ethertype 分布:
  0x0800  3483
  0x86DD     9
```

802.11 帧 0 个，`0x7496`/`0x58CB` 全部消失。

## 两条经验

**1. 不要把「解析失败」当解析器的 bug，先看字节。**
第一反应是"我的解析器错了吗"，实际是数据源有两种封装。
验证方法永远是：把可疑数据的原始字节 `hex` 出来看一眼，比猜快十倍。

**2. 数字先要可信，再谈好看。**
解析率从 34% 涨到 99.94% 是好事，但同一批改动也让包数虚高了 3 倍。
两个数字一起看才发现：救回来的 11.6 万帧里，有 4 万多是重复的。

## 对解析器的影响

- `pcappeek/link.py`：不假设 `linktype` 可信，按字节特征判断封装
  - 以太网：第 13–14 字节是已知 ethertype
  - 802.11 Data：帧控制低字节 `& 0x0C == 0x08`，且对应偏移处有 LLC/SNAP 头
- 自己抓包一律用 `--comp nics`；别人给的 pcap 可能混杂，交给 `link_payload` 兜底
- 报告里必须区分「抓到的帧数」与「去重后的包数」，不能混为一谈
